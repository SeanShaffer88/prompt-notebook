# Public Prompt Notebook

The hosted edition of [Prompt Notebook](https://github.com/SeanShaffer88/prompt-notebook).

- No-key sample mode is explicitly simulated and never calls a model.
- Live mode supports 13 connections: Anthropic, OpenAI, Gemini, OpenRouter, Groq, Mistral, DeepSeek, xAI, Together AI, Fireworks AI, Cerebras, SambaNova, and NVIDIA NIM. Keys are separate in tab memory, sent over HTTPS only on model operations, and never saved or exported. Reloading or clearing connections removes them. Each adapter has a fixed official API destination and rejects redirects and arbitrary endpoints. OpenAI and xAI Responses requests set `store: false`.
- Browse models from Instructions or Settings. A keyless public OpenRouter catalog provides hundreds of searchable text-capable models and refreshes every 10 minutes; a dated snapshot is used if the catalog is unavailable. Batch-only and non-text entries are filtered out. Direct connections include starter IDs; other supported model IDs can be entered manually. Catalog presence does not guarantee access, latency, credits or model-specific compatibility. This notebook handles text-in/text-out, not image/audio generation, embeddings, or model-specific tool workflows. Slow reasoning models may exceed its interactive timeout.
- A model labeled **via OpenRouter** requires an OpenRouter key, regardless of who made the model. OpenRouter forwards requests to its model hosting providers under its own routing and data policies. Direct-provider keys are never forwarded to OpenRouter or other connections.
- **Compare models** sends one saved prompt version and the same input values to 2–4 distinct provider/model combinations concurrently. All required keys and target IDs are checked before any model call. Results retain their order and are saved side by side with model/provider identity, usage, latency, exact rendered prompt and version/input snapshots. A failed model is shown separately without discarding successful answers. Source prompt versions remain unchanged. No-key sample comparisons are simulated canned answers; connect keys to compare actual model behavior.
- Settings chooses the default provider/model for new versions. Each saved version pins its provider; old versions remain Anthropic versions. To change a prompt's provider, choose it under Instructions and save a new version. Experiments and workflows can span providers when all required keys are connected; missing keys fail before starting the batch. Reference corrections use the provider of the original version.
- Saved prompts, versions, corrections, examples, experiments and workflows live in Cloudflare D1. Each browser receives a random HttpOnly/Secure/SameSite cookie; its hash selects an isolated workspace. There is no shared global notebook and no unauthenticated workspace-list API.
- Cookies preserve access for up to 180 days. Clearing the cookie loses access; export important work. This alpha has no cross-device recovery, sign-in, or backup import.
- Public limits: 1,000 workspaces, 120 operations per workspace/day, 3 examples per comparison, 128 KB requests, bounded per-workspace storage and model-operation duration. A lease serializes operations within each workspace.

## Development and deployment

Use the included Sites/Vinext runtime. The original starter README documents installation, local D1 migrations and builds. Run `node --test test/notebook.test.mjs` to verify the portable notebook service. Run `npm run build` before previewing with `npm start`. The deployment manifest binds D1 as `DB`; migrations are in `drizzle/`.

Production requires no operator model key or connection to the owner's computer. The standalone local application remains available in the parent repository.

## Validation

Service tests cover the sample correction/experiment/workflow loop, all three API request/response contracts, fixed destinations, blocked/empty responses, provider failure handling, key routing in mixed-provider workflows, legacy version compatibility, secret exclusion, and independent visitor state. HTTP checks against the built local Worker exercise separate cookie sessions, data persistence, stale workflow detection/retest, exports and cross-origin rejection. Successful paid-provider calls require visitor credentials; adapter tests use deterministic provider responses.

### Review model comparisons
Rate each completed response from 1–5, pick one winner, and save that winner into the notebook. Ratings and winner choices persist. Saved best responses retain the exact output, prompt/input snapshot, model, sample label, and rating at save time. Changing a winner leaves earlier saved responses intact; repeated saves of the same response are deduplicated. Prompt exports include reviews and saved responses. Failed responses cannot be rated or selected.

### Improve prompts from reviewed comparisons
After rating a response and choosing a winner, use Suggest improved prompt with optional feedback. The suggestion records the winner, all ratings and outputs as a snapshot, uses the original version's model, and preserves template variables. Review and edit it, then Save candidate & set up test. The original version and source example are preselected in Experiments; both versions run on the candidate's pinned provider/model/token limit. The source example is labeled as used for improvement. Add fresh examples to assess generalization. Reference answers support human review and are not automatic quality scores. Candidates do not become active automatically. Sample suggestions and runs remain explicitly simulated.

### Activate experiment winners and roll back
Completed experiments allow a human to pick either tested version as winner, then activate it separately. Activation records the actual previously active version and offers one-click rollback while that activation remains current. All versions, runs and results are retained. History also offers Make version active for any saved version. Stale active-version changes and incomplete test runs are rejected. Sample outputs cannot establish quality; review real responses before promoting. Activations affect future workflow runs and existing workflow staleness indicators.

### Slice 1: workflow quality checks
Test each affected workflow before promotion using the current active version and proposed experiment winner, without activating either. All step versions and model defaults are pinned. Step contracts support text rules, JSON validity and required top-level fields. Per-step user-supplied token prices enable estimated cost budgets; latency budgets use summed model-call latency. Missing prices remain unknown. Changed outputs require human review; previously passing rules or budgets that fail are regressions. Sample results cannot establish quality. Checks become stale after relevant version, model default, winner or contract changes. Experiment summaries show rule results and missing workflow coverage.

### Slice 2: reusable evaluations
Save 1–3 checked examples as a named dataset snapshot. Experiments can use that dataset and repeat each example 1–3 times, up to six example/trial pairs. Every trial is retained and shown independently. History offers capture of failed or successful responses as regression examples with optional expected output and rule checks; source run provenance is preserved.

### Slice 3: human review
Score completed responses on accuracy, clarity, completeness and tone, with optional notes. Reviews persist and are included in subsequent comparison-based prompt suggestions. Blind model and version review stores a randomized order and masks identity labels in the comparison view; outputs may identify themselves, and exports retain provenance. Reveal version identities before activation. Experiments show a baseline-to-candidate instruction diff; unchanged prefix/suffix context is retained around the changed block.

### Slice 4: portable bundles
History & export can download a versioned bundle and preview an import. Bundles include prompts, versions, workflows, run history, datasets, reviews and evaluation results; connection settings and keys are excluded. Imports validate schema, sizes and graph references, assign new IDs, retain existing work, and mark imported workflow checks stale. Public imports are limited to 110 KB. Importing does not execute AI calls or connect keys.

### Workflow activation gate and manual overrides
Activation from Experiments, Notebook and History now checks every currently connected workflow. The latest check for the proposed version must match current pinned versions, settings and contracts, finish both branches, and contain no regressions or failing/inconclusive checks. Simulated checks require an override. Missing checks, stale checks and new dependencies block normal activation. A manual override requires a nonblank reason (up to 3000 characters); the server recomputes readiness and saves the reason, timestamp, previous/new versions and exact blocker/check snapshot in activation audit history. Full exports, prompt exports and portable bundles retain this history. Dedicated experiment rollback remains available without a new check. UI readiness is advisory; the server enforces every activation request.

### Workflow readiness batches and ten quality-of-life tools
Test all affected workflows queues missing/stale checks, reuses current results, and executes one workflow per server request. All selected inputs and provider keys are checked before the batch starts. Progress persists; resume after interruption, or cancel between workflows (in-flight billable calls finish). A changed winner, active version or queued workflow plan stops the batch. Retry flagged checks is separate and deliberate. Normal activation stays gated; changed text requires an acceptance note and regressions cannot be accepted away. Existing manual activation overrides still require a saved reason.
The ten additions are coverage tables; optional 0–720-hour check expiry (positive values only); saved reusable workflow inputs; live batch progress; cancellation; flagged-check retries; regression filtering; per-step output diffs; review notes/decisions/history; and downloadable readiness reports. Reports contain inputs/outputs, never provider keys. Bundles retain batches; imported running batches are stale.

### Change-triggered checks (open tab only)
Enable Auto checks to queue affected workflows when versions, active prompts, workflow settings/inputs or provider model preferences change. Keys remain only in tab memory; the browser driver stops when the tab closes. Default debounce is 10 seconds and cap is two automatic workflow checks per hour (each may make up to 12 billable calls). Settings are opt-in per visitor; pause retains queued work. Rapid changes coalesce per workflow. Missing keys/inputs block jobs before spending calls. Metadata and results persist for the next visit.
Proposed versions compare with current active versions. Active workflow monitors compare with the last accepted passing snapshot; first checks need a human baseline review, and failed/simulated results cannot establish baselines. Regressions/check failures create in-app alerts only. Marking read, acknowledging or muting alerts never clears activation failures. Importing bundles does not enable automatic checks or execute imported queued jobs.
Ten additions: change log, dependency view, debounce control, coalescing queue, pause/resume, unread alert inbox, acknowledgment notes, per-workflow alert mutes, hourly run cap, and last-passing-snapshot comparison. New audit collections are portable; automatic settings and keys are not imported. Browser key forwarding now covers batch and automatic execution routes, with a contract test preventing accidental omission or export leakage.

### Regression repair proposals and approval
The Repairs view links regression alerts to inactive prompt-fix candidates. Opt-in automatic suggestions/testing run only in an open tab with Auto checks enabled and unpaused. Separate defaults allow one automatic suggestion and two workflow test pairs per hour. Missing accepted passing baselines or incomplete execution evidence block generation before AI calls. Operational failures are not treated as prompt-output regressions.
Suggestions use source/last-passing evidence and editable goals, while protecting source variable names. Held-out inputs are excluded from generation. Tests compare the last-passing target prompt with the repair across every connected workflow, keeping other steps pinned to current versions. Each workflow has a source case and an optional distinct held-out case. Previews show call counts, output-token caps and approximate costs when manual token prices exist.
Review the prompt diff, all workflow results and held-out coverage, choose the candidate or shared last-passing version, complete the checklist and save a reason. Approval does not activate anything. Missing/stale/failed/simulated evidence is rejected; workflow/baseline/candidate changes invalidate approval. Even a manual activation override cannot bypass repair approval. A separate activation button retains prior versions and an audited rollback. Repair status, provenance, goals, variable protection, diffs, cost preview, held-out cases, retry controls, checklist and downloadable history are the ten added tools. Bundles retain evidence but invalidate imported repair approvals and never enable automatic repairs.

Headings, titles, buttons, and tabs render in Proper Case, including dynamic results. Acronyms, brand names, model IDs, variables, and saved prompt content retain their spelling.

### Quality Lab: Ten Improvements In Three Slices
Slice 1 adds versioned reusable evaluation suites (1–12 cases), resumable paired comparisons (1–10 repeats; up to 30 pairs), and session/evaluation spend controls. Confidence uses a two-sided sign test on example-level trial-majority outcomes, with a conditional Wilson 95% interval. Fewer than six discordant examples, missing checks, failures, or sample evidence stay inconclusive. Model/version settings are pinned; compare matching models for prompt-only attribution. Repeated trials are grouped, not treated as independent examples. Results are exploratory on curated inputs and do not prove generalization.
Spend controls apply to every live model call, including automated checks and suggestions. The explicit spend session is shared across workspace tabs; it does not reset when a tab closes. User-supplied provider/model prices reserve UTF-8 input bytes plus maximum output tokens before starting a call. Reported usage adjusts estimates; failed/unknown usage keeps the reservation. Dollar-capped calls block when prices or earlier session costs are unknown. Session reset needs a saved reason. The ledger retains the latest 60 live calls. Limits schedule requests; they cannot guarantee provider invoices. Sample mode is free and does not consume budgets.
Slice 2 adds failure clustering by alert kind/normalized messages, a prompt-to-workflow/downstream/suite/experiment/repair impact map, injection test suite generation, and structured output validation. Injection cases test three fixed attacks across at most four original cases, retaining original behavioral checks and rejecting an attack marker. These are heuristics, not a security certification. JSON schemas support type, properties, required, additionalProperties, items, enum, min/max length and item counts, and numeric bounds; unsupported keywords fail validation. Field paths appear beside each branch result. Schema checks also work in saved test and workflow contract JSON.
Slice 3 adds explicit ordered model routing, notebook-wide lexical search with source evidence, and named release snapshots. Routing can match input phrases and filter by manually priced cost ceilings; quality requirements are human guidance. Fallback is limited to connection/timeout failures, HTTP 429 and provider 5xx; authentication, refusals, invalid output and spend-limit errors stop the chain. Each attempt is retained. Ordinary prompt/workflow runs keep their pinned models. Search covers prompts, versions, responses, corrections, reviews, experiments and evaluation results (all words must match; 40 results maximum).
Release snapshots capture active assignments, workflow configurations, suite revisions and evidence references, with at most ten snapshots per public workspace. Preview, a restore reason and unchanged workspace configuration are required. A staged restore reuses activation gates and cannot bypass repair approval; any rejection leaves the original state unchanged. Existing additions and run history remain. Previous configuration is saved in restore audit records. Connections, routing rules and spend settings are excluded from restoration.
Portable bundles include suites, evaluation evidence, routing records and releases. Imports remap graph IDs, retain JSON schemas, and mark evaluations stale so imported work never resumes. Spend settings/ledgers and keys are not imported.
